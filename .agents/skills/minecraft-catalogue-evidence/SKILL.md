# Minecraft catalogue evidence

Read AGENTS.md, docs/README.md and docs/Research-and-Verification.md before changing records. This is research/catalogue maintenance, not mod installation or a guarantee of compatibility.

## Reconcile identities without losing observations

Use exact primary project routes and file/release identities rather than display names, spreadsheet rank or fuzzy name matching. Keep Java versus Bedrock, loader, target Minecraft version, forks/ports, pack/mod/library/tool types and source dates separate. A built-in feature or discovery route is not automatically an independent installable mod.

Before consolidating records, inventory attached source observations, favorites, caution notes and unresolved identities. Retain duplicate observations' provenance even when their project identity is shared. Ambiguous multi-project links remain reviewable. Do not overwrite historic claims with a newer fact: attach dated current evidence alongside the old observation.

For a requested feature or dependency, inspect the current exact official release metadata; inspect actual files/source when the claim requires it. Preserve distinctions among imported source note, official metadata checked, actual files inspected and native tested. Neither a favorite nor a green import receipt establishes native game compatibility.

## Validate a catalogue change

Inspect the relevant docs/ JSON schema, source-view and import-verification receipts before editing. Compare record and observation counts, stable IDs, unresolved rows, favorites and source links before/after; explain any intentional delta. Do not conflate overlapping category totals with unique mods. Check references across index and detail shards.

The repository includes archived verification tools such as docs/catalogue-cache-revision-tools.zip. Inspect archive contents and provenance before using an extracted helper; do not invent a test command or silently treat packaged historical test results as a fresh run. Read the current HTML/JavaScript request paths to identify the maintained index and all detail shards.

When changing published data, update its shared revision using the documented cache tool, preserve equivalent search/detail behavior, and verify returning-browser freshness after deployment. Exercise delayed loads, search spelling/typography and matching details, including non-Latin text. Static data validation is separate from browser acceptance and live wiki publication.

## Publication and boundaries

Keep implementation targets and actual project code in their owning repositories. Catalogue recommendations can link evidence, but cannot substitute for a project's target comparison and runtime gates. Never redistribute paid/proprietary mod archives, private account material or personal saves. Retain original import sources until reconciliation and any required retirement approval are complete.

Report exact changed records, preserved counts, source dates, checks actually run, remote revision and published-site/wiki verification separately. Leave unresolved identities and untested compatibility explicitly unresolved.
